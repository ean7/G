# Система івентів Inve.Store

## Базова логіка

Івенти Inve.Store — це не один разовий захід, а постійна система точок входу, утримання та прогріву клієнтів. Система івентів має працювати щомісяця, підтримувати клієнтів з абонементом і бути пов’язаною з Telegram-ботом, оплатами, CRM, SaaS-кабінетом, аналітикою та адмін-управлінням через Codex.

## Типи івентів

### 1. Щомісячний acquisition event

Щомісяця створюється новий публічний івент як точка входу для нової аудиторії.

Цілі:

- залучити нових підприємців, інвесторів або партнерів;
- зібрати ліди через лендінг і Telegram-бот;
- продати квитки;
- перевести учасників у SaaS-діагностику, абонемент, консалтинг або інвестиційну воронку.

### 2. Регулярні івенти для клієнтів з абонементом

Для тих, хто вже купив абонемент, проводяться регулярні закриті івенти.

Цілі:

- підвищити цінність абонементу;
- підтримувати залученість клієнта;
- проводити навчальні, стратегічні або діагностичні сесії;
- збирати додаткові дані для дашбордів і автодіагностики;
- переводити клієнтів до консалтингу, інвестицій або партнерських продуктів.

## Мінімальна архітектура системи

1. **Event landing pages** — сторінки щомісячних івентів із темою, цінністю, датою, програмою, спікерами, ціною та CTA `КУПИТИ квиток`.
2. **Member events** — закриті івенти для клієнтів з абонементом, доступні через SaaS-кабінет або персональні посилання.
3. **Telegram-бот** — реєструє учасників, надсилає нагадування, пуш-повідомлення, презентації й наступні CTA.
4. **Платіжна система** — приймає оплату квитків, абонементів і консалтингових продуктів.
5. **CRM / база лідів** — отримує всі заявки, реєстрації, кліки CTA, покупки, відвідування та статуси комунікації.
6. **Аналітика** — зберігає UTM, джерело, кампанію, події CPL, CAC, attendance, retention і post-event conversion.
7. **SaaS-кабінет** — показує клієнту релевантні івенти, матеріали, рахунки, дашборди та наступні дії.
8. **Codex admin workflow** — дозволяє керувати контентом сайту, структурою сторінок і конфігурацією івентів через зміни в репозиторії.

## Ключові події

| Етап | Подія | Аналітичний сенс |
| --- | --- | --- |
| Event created | Створено щомісячний або закритий івент | Початок життєвого циклу івенту |
| Visit | Відвідувач відкрив івент-лендінг | Початок сесії та attribution |
| CTA click | Натиснув `КУПИТИ квиток` або `Зареєструватися` | CPL для landing page |
| Bot start | Запустив Telegram-бота | CPL для Telegram-воронки |
| Registration | Поділився контактом | Лід готовий до комунікації |
| Push sent | Бот надіслав пуш | Touchpoint у комунікації |
| Push clicked | Користувач натиснув пуш | Engagement |
| Payment started | Почав оплату | Намір купити квиток або абонемент |
| Ticket paid | Оплатив квиток | CAC для acquisition event |
| Subscription active | Має активний абонемент | Доступ до member events |
| Event attended | Відвідав івент | Якість залучення |
| Deck sent | Отримав презентацію або матеріали | Післяівентний touchpoint |
| SaaS action | Виконав дію в SaaS після івенту | Перехід у наступну воронку |

## Метрики

- **CPL landing** — натискання кнопки `КУПИТИ квиток` або `Зареєструватися` на лендінгу.
- **CPL bot** — реєстрація або старт у Telegram-боті.
- **CAC event** — фактична купівля квитка на щомісячний івент.
- **Subscriber activation** — клієнт з абонементом зареєструвався на закритий івент.
- **Attendance rate** — частка зареєстрованих або покупців, які відвідали івент.
- **Push engagement** — відкриття або кліки пуш-повідомлень у Telegram-боті.
- **Post-event conversion** — частка учасників, які після івенту перейшли в SaaS, консалтинг або інвестиційну заявку.
- **Retention by events** — вплив регулярних івентів на продовження абонементу.

## Система пуш-повідомлень у Telegram-боті

Пуш-повідомлення мають працювати на всіх стадіях комунікації з клієнтом:

1. **До івенту** — підтвердження реєстрації, нагадування, програма, спікери, дедлайн оплати.
2. **Під час івенту** — посилання на трансляцію, матеріали, питання, CTA до наступного кроку.
3. **Після івенту** — подяка, презентація, запис, опитування, запрошення в SaaS або консультацію.
4. **Для абонентів** — закриті події, нагадування про сесії, нові матеріали, статуси діагностики.
5. **Для інвестиційної воронки** — запити документів, статуси заявки, оновлення щодо угоди або аудиту.

## Дані, які потрібно збирати

- event id, тип івенту, дата, формат і статус;
- UTM source, medium, campaign, content, term;
- referrer і landing page URL;
- Telegram user id, username, ім’я, телефон або email, якщо користувач надав ці дані;
- статус оплати, сума, валюта, payment provider transaction id;
- статус квитка або доступу: reserved, paid, refunded, attended, no-show;
- статус абонементу для закритих івентів;
- дата і час кожної події;
- пуш-повідомлення: delivered, clicked, ignored;
- наступний крок після івенту: презентація відправлена, SaaS signup, консультація, інвестиційний інтерес.

## Адмін-управління сайтом через Codex

На першому етапі Codex використовується як admin workflow для керування сайтом через репозиторій:

- створення або оновлення сторінок івентів;
- редагування текстів, CTA, програм і блоків;
- додавання конфігурацій івентів;
- оновлення документації, аналітичних подій і вимог до інтеграцій;
- підготовка PR із контрольованими змінами.

У наступних ітераціях можна винести контент івентів у структуровані файли, наприклад `data/events.json`, щоб Codex міг оновлювати івенти без ручного редагування HTML.

## Питання перед реалізацією системи івентів

Перед кодом потрібно затвердити:

1. Які типи івентів запускаємо першими: тільки щомісячні публічні чи одразу також закриті для абонентів?
2. Яка структура сторінки одного івенту: дата, програма, спікери, ціна, FAQ, форма або кнопка оплати?
3. Чи потрібен каталог усіх івентів на сайті?
4. Яка платіжна система буде першою?
5. Telegram-бот: створюємо нового чи підключаємо наявного?
6. CRM або таблиця, куди мають падати ліди, оплати й пуш-статуси.
7. Які пуш-повідомлення запускаємо в MVP: до івенту, після івенту або для абонентів?
8. Як Codex має керувати контентом: напряму HTML чи через структуровані `data`-файли?
